# CyTube & watchparty — comparative research

Targets: `/code/Projects/VideoSync/refs/cytube` (calzoneman/sync) and `/code/Projects/VideoSync/refs/watchparty` (howardchung/watchparty). All `file:line` citations are relative to each project's own repo root.

## 1. Overview

### cytube
Node.js server (`src/*.js`), CoffeeScript client player layer (`player/*.coffee`, compiled via `bin/build-player.js`), legacy jQuery UI (`www/js/*.js`), Pug templates, Socket.IO v4 (`package.json:26`), MySQL via knex + optional Redis pub/sub for clustering. Version `3.86.1` (`package.json:5`). License MIT (`LICENSE:1-3`). Shallow clone shows one commit `589f999 "Fix bitchute queuing"`, `2025-11-06`. `NEWS.md` changelog frozen at `2022-09-21`; `.travis.yml:11-14` still targets EOL Node 12/14/15 on a dead CI provider. Signal: small, low-bandwidth maintainer doing targeted fixes, not active feature development, on a ~10-year-old production codebase.

### watchparty
TypeScript throughout. Server: Node.js + Express 5 + socket.io 4.8.1 + PostgreSQL (`pg`) + Redis (`ioredis`) (`package.json:6-10`). Client: React 18 (class components) + Vite 7. Also bundles `hls.js`, `dashjs`, `webtorrent`, `mediasoup-client`, Firebase auth, Stripe, `discord.js`. License MIT (`LICENSE:1-3`). Shallow clone, one commit `eb20aefe0 "use serverpath"`, `2026-07-30`. `.github/workflows/nodejs.yml` + `.github/dependabot.yml` present — active CI. `CHANGELOG.md` stale since April 2023 despite recent dep bumps (Vite 7/React 18/Express 5) — doc lag, not code lag. **No browser extension exists in this repo** — arbitrary-site playback is solved via a cloud "VBrowser" and WebRTC screen-share instead (see §8).

## 2. Transport & message schema

### cytube
Socket.IO v4, one channel = one socket.io room, `sio.instance.in(ns).emit(msg, data)` (`src/channel/channel.js:717-723`).

Media change (server→client, full state), `broadcastAll("changeMedia", update)` where `update = media.getFullUpdate()` (`src/channel/playlist.js:363-365`, `src/media.js:72-77`):
```js
{ id, title, seconds, duration, type,
  meta: { restricted, codec, bitrate, scuri, embed, gdrive_subtitles, textTracks, audioTracks, direct?, thumbnail? },
  currentTime, paused }
```
Leader→server time report, `mediaUpdate`, `TYPE_MEDIA_UPDATE` (`src/channel/playlist.js:47-52`):
```js
{ id: "string", currentTime: "number", paused: "boolean,optional", type: "string,optional" }
```
sent from `sendVideoUpdate()` (`www/js/util.js:1462-1471`). Server→all heartbeat, `mediaUpdate` = `media.getTimeUpdate()` (`src/media.js:65-70`): `{ currentTime, paused }`, forwarded from leader (`src/channel/playlist.js:853-874`) or generated by server's own timer every `UPDATE_INTERVAL` (default 5s, `config.template.yaml:180`).

Leader assign: client→server `assignLeader { name }` (`src/channel/playlist.js:43-45`); server→all `setLeader` (bare username string, `""` = none, `:832`, `:300`). Chat: client→server `chatMsg { msg, meta? }` (`src/channel/chat.js:14-17`); server→all `chatMsg { username, msg, meta, time }` (`:302-311`).

### watchparty
Socket.io, one **namespace per room** (`io.of(roomId)`), `transports: ["websocket"]` only (`server/server.ts:55`, `src/components/App/App.tsx:337`). No SSE/polling fallback.

Client emits `CMD:*`, server rebroadcasts `REC:*` (`server/room.ts:263-346`):
```
CMD:play → ()            CMD:pause → ()            CMD:seek → number
CMD:playbackRate → number  CMD:loop → boolean       CMD:ts → number (self-reported time, no lock check)
CMD:host → string (media URL / vbrowser://…)
```
```js
socket.broadcast.emit("REC:play", this.video);      // room.ts:751-760, excludes sender
socket.broadcast.emit("REC:pause");                  // room.ts:762-771
socket.broadcast.emit("REC:seek", data);              // room.ts:773-781
this.io.of(this.roomId).emit("REC:playbackRate", Number(data)); // room.ts:783-795, INCLUDES sender
io.of(roomId).emit("REC:tsMap", this.tsMap);          // room.ts:94-107, 1Hz heartbeat
```
`HostState` (sent on connect / any `CMD:host`, `global.d.ts:70-79`):
```ts
interface HostState { video: string; videoTS: number; subtitle: string; paused: boolean;
  isVBrowserLarge: boolean; controller?: string; playbackRate: number; loop: boolean; }
```
`tsMap: Record<clientId, number>` — normalized/extrapolated timestamps, not raw reports (§3). On connect, server dumps `REC:host`, `REC:nameMap`, `REC:pictureMap`, `REC:tsMap`, `REC:lock`, `chatinit` (last 100 msgs), `playlist` (`server/room.ts:209-217`). No custom ping/pong event exists.

## 3. Clock synchronization

### cytube
**ABSENT.** No RTT measurement, no min-RTT sampling, no clock-offset estimation anywhere (grep for `ping|latency|rtt|clockOffset` across `src/`, `player/`, `www/js/` yields only Prometheus DB/HTTP metrics and socket.io's `pingTimeout`, deliberately raised to 120000ms to *avoid* spurious reconnects, `src/io/ioserver.js:266-273`). Model = server-authoritative wall-clock with **zero network-delay compensation**: leader self-reports `currentTime` every 5s (`www/js/callbacks.js:601`), server trusts it verbatim (`media.currentTime = data.currentTime`, `src/channel/playlist.js:869`) and rebroadcasts unmodified. With no leader, server advances time itself via `Date.now()` deltas (`_leadLoop`, `src/channel/playlist.js:1141-1183`):
```js
var dt = (Date.now() - this._lastUpdate) / 1000.0;
this.current.media.currentTime += dt;
this._lastUpdate = Date.now();
```
No RTT is added/subtracted on either send or receive path.

### watchparty
**No RTT-based sync either** (no ping/pong, no latency measurement). Instead: 1Hz client position heartbeat, unconditional:
```js
window.setInterval(() => { if (this.state.roomMedia) {
  const toSend = this.getRoomTSToSet(this.Player().getCurrentTime());
  this.socket.emit("CMD:ts", toSend); } }, 1000);  // App.tsx:866-871
```
Server normalizes for elapsed time since last broadcast (one-way extrapolation, not RTT):
```js
// server/room.ts:805-824
const timeSinceTsMap = Date.now() - this.lastTsMap;
this.tsMap[socket.clientId] = data - timeSinceTsMap / 1000 + 1;
```
rebroadcast every 1s regardless of activity (`room.ts:94-107`). Client computes a "leader" position as the **median** of all `tsMap` values (max for ≤2 participants) — a decentralized vote, not a single clock:
```js
// App.tsx:1954-1959
getLeaderTime = () => this.state.participants.length > 2
  ? calculateMedian(Object.values(this.state.tsMap))
  : Math.max(...Object.values(this.state.tsMap));
```
(`calculateMedian`: `src/utils/utils.ts:342-362`). Server is a relay/aggregator, not authoritative for time.

## 4. Drift correction policy

### cytube
Deadband + **hard seek only, no playbackRate nudging** (grep for `playbackRate|setSpeed` across player layer: no hits). `handleMediaUpdate` (`player/update.coffee:75-104`):
```coffee
diff = (time - seconds) or time
accuracy = USEROPTS.sync_accuracy
accuracy = Math.max(accuracy, 5) if PLAYER instanceof DailymotionPlayer
if diff > accuracy then PLAYER.seekTo(time)
else if diff < -accuracy
    time += 1 unless PLAYER instanceof DailymotionPlayer
    PLAYER.seekTo(time)
```
Constant: `USEROPTS.sync_accuracy` default **2s** (`www/js/data.js:175`), user-configurable. Dailymotion gets a 5s floor (Flash keyframe imprecision, comment `:97-99`). Whole mechanism disable-able via `USEROPTS.synch` (default true). Pause/play corrections are also hard `seekTo`+`pause`/`play`.

### watchparty
Two tiers, both client-side. **Tier 1 — playbackRate nudge**, deadband 0.5s, cap 1.1x, only when `roomPlaybackRate === 0` and not a livestream:
```js
// App.tsx:762-781
const delta = leader - data[clientId];
let pbr = 1;
if (delta > 0.5) { pbr += Number((delta / 10).toFixed(2)); pbr = Math.min(pbr, 1.1); }
if (this.Player().getPlaybackRate() !== pbr) this.Player().setPlaybackRate(pbr);
```
Only pulls laggards forward, never slows down clients ahead. **Tier 2 — manual hard seek**, deadband **10s**, UI-only (no auto-trigger):
```js
// Controls.tsx:107-112
const behindThreshold = 10;
const isBehind = behindTime > behindThreshold;
```
Sync button turns blue when behind; user must click it (`Controls.tsx:160-176`). **No automatic hard-seek** exists — real gap vs. cytube's always-auto-correcting model.

## 5. Echo suppression

### cytube
No ignore-flag/timeout, no sequence numbers — achieved by **strict role gating** (server's `broadcastAll` = `io.in(room).emit`, includes sender, so the leader receives its own echo but discards it):
- Only leader sends: `sendVideoUpdate()` early-returns `if (!CLIENT.leader) return;` (`www/js/util.js:1463-1465`), gated per-provider event handler too (e.g. `player/youtube.coffee:46-53`).
- Only non-leader applies incoming updates: `if CLIENT.leader or not USEROPTS.synch then return` (`player/update.coffee:74-76`).
- Server mirrors this: only accepts `mediaUpdate` from the current leader socket, `if (this.leader !== user) return;` (`src/channel/playlist.js:853-855`).

### watchparty
No ignore-flag/sequence numbers either. **(a)** Asymmetric broadcast + optimistic local apply for play/pause/seek: server uses `socket.broadcast.emit` (excludes sender, `room.ts:752,763,778`), while the issuing client applies locally immediately without waiting for its own echo:
```js
// App.tsx:1766-1789
if (shouldPlay) { this.socket.emit("CMD:play"); this.localPlay(); }
this.Player().seekVideo(target); this.socket.emit("CMD:seek", toSend);
```
**(b)** For idempotent state (playbackRate/loop/host) the server broadcasts to everyone *including* sender, and the client relies on the broadcast to apply it — safe because re-applying the same value is a no-op. **(c)** Explicit stale-update suppression: 1s `preventTSUpdate` flag blocks late `CMD:ts` from a just-replaced video from corrupting the new video's `videoTS` (`server/room.ts:536-549`); a similar "ignore, it's probably a reconnection" guard exists for WebRTC host state (`App.tsx:437-452`).

## 6. Conflict resolution without a host

### cytube
Has a hybrid leader model, not pure LWW. Playback timebase is single-writer: either a moderator-assigned leader reports time, or, absent one, **the server itself** is authoritative via a 1s `_leadLoop` (`src/channel/playlist.js:1141-1183`). Leader assignment requires `permissions.canAssignLeader` (rank ≥ `leaderctl`=2, `src/channel/permissions.js:40`); attempting it without permission gets you kicked (`playlist.js:788-790`). Leader gets a temp rank boost to ≥1.5 while leading (`:825-830`), restored on removal. Losing the leader (part/disconnect) auto-falls-back to server timekeeping (`onUserPart`, `:317-321`) — not renegotiated among peers. Playlist skip/jump is **separately** permission-gated (`canSkipVideo`, rank≥1.5) and not leader-exclusive — any sufficiently-ranked user can force a transition, immediately overwriting in-flight state. Tie-break = **role/permission-based single-writer per responsibility**, no vector clocks, no timestamp comparison, no CRDT.

### watchparty
**No host/authoritative-controller for media control** — any client can emit `CMD:play/pause/seek/host`, server executes immediately and broadcasts: pure **last-write-wins**, zero conflict detection (`server/room.ts:263-340`). Two simultaneous plays/pauses both get applied in arrival order; the loser's optimistic local state is silently overwritten by the next broadcast it receives. Closest thing to a host: **room lock** (`this.lock` = an owner-chosen uid), gates every `CMD:*` handler via `validateLock()` checking `socket.uid === this.lock` (`room.ts:224-346`) — but unlocked rooms (the default) have **zero access control**, and locked rooms have only one allowed writer so conflicts are moot by construction, not resolved. `videoTS` (canonical position for late joiners) is set unconditionally by the most recent `CMD:seek`, and only ratchets forward via heartbeats unless negative/livestream (`room.ts:773-781, 813-817`) — a straggler can't regress the room's position via heartbeat, only via explicit seek.

## 7. Buffering / readiness gating

### cytube
Essentially **ABSENT**. No polling/aggregation of client readiness before playback starts. Only nod: fixed **3s lead-in** on server autolead (`time = time || (media.seconds > 0 ? -3 : 0)`, `src/channel/playlist.js:1099`); clients told to load-but-not-play while `currentTime < 0` (`waiting = data.currentTime < 0`, `player/update.coffee:52-62`); a blind timer transitions -3s→0s after 3 real seconds regardless of actual buffer state (`playlist.js:1157-1163`). Similarly a blind 2s grace period before advancing past a video's end "to allow slightly off-sync clients to catch up" (`:1176-1180`). `playerReady` event just triggers a fresh `changeMedia` resend, not aggregate readiness (`:280-282`).

### watchparty
**ABSENT — no room-wide readiness gating.** `loading` state is a purely local per-client UI spinner (`App.tsx:119,193,460,932,944,1727,1951`), never sent to server, never blocks others. Each client plays as soon as it individually is ready; laggards are caught by the drift-correction system after the fact (§4). `getTimeRanges()` (buffered ranges, `Player.ts:22`) is used only for a visual progress-bar overlay (`Controls.tsx:113-129`), never for sync decisions.

## 8. Provider coupling

### cytube
Two parallel, hand-synchronized registries keyed by 2-letter type codes, never validated against each other automatically. Client: `player/base.coffee` defines `window.Player`; `player/update.coffee:1-20` `TYPE_MAP` (`yt→YouTubePlayer, vi→VimeoPlayer, fi→FilePlayer, ...`); `window.loadMediaPlayer(data)` (`:22-38`) instantiates `TYPE_MAP[data.type](data)`. Server: `src/get-info.js:400-436` `Getters` object, same codes, mostly delegating to the `@cytube/mediaquery` package. Adding a provider = edit both files + write a new `.coffee` subclass + recompile the concatenated bundle (`bin/build-player.js`). This targets **embeds/IDs** (YouTube video ID, Vimeo ID, direct file URL) — it does not scrape arbitrary third-party page DOM; there is no extension, no MutationObserver, no SPA-navigation/iframe/shadow-DOM handling anywhere in this codebase.

### watchparty
Seam is a **two-implementation abstract `Player` class** (`src/components/App/Player.ts`), not per-arbitrary-site DOM adapters. `HTML` (`HTML.ts`) wraps one fixed native `<video id="leftVideo">` (constructed once, `App.tsx:266`), handling direct file/HLS(hls.js)/DASH(dashjs)/WebTorrent/WebRTC uniformly via `.src`/`.srcObject` swap. `YouTube` (`YouTube.ts`) wraps `window.YT.Player`. Selection is a hardcoded ternary, no registry: `usingYoutube() ? YouTubeInterface : HTMLInterface` (`App.tsx:267-273`). **No per-site DOM adapter, no MutationObserver, no SPA-nav/iframe/shadow-DOM handling** — because there's no extension. "Any site" is instead solved by: (1) server-side URL extraction for a small allowlist — Reddit (`room.ts:615-636`), Twitch via `twitch-m3u8` + proxy (`:637-666`), YouTube Data API (`server/utils/youtube.ts`); (2) WebRTC screen/tab/file-share, P2P or via a MediaSoup SFU (`App.tsx:1133-1508`); (3) **VBrowser** — a shared ephemeral cloud VM running headless Chrome (Neko/`m1k1o/neko`), video/audio/input remoted over WebRTC to all participants (`server/vm/*`, `src/components/VBrowser/*`). This sidesteps the DOM-scraping problem entirely by remoting a real browser instead.

## 9. Room, identity & auth model

### cytube
Room creation: authenticated web flow `POST /account/channels` → `handleNewChannel` (`src/web/account.js:250-320`); checks channel-ban, reserved-name regex, and **cap of `max-channels-per-user: 5`** (`config.template.yaml:126`, waived for `global_rank==255`). Persistence: registered channels store state as key/value DB rows (`src/channel-storage/dbstore.js`), hard **1 MiB per-channel size limit** (`SIZE_LIMIT=1048576`, `:7`, `ChannelStateSizeError` at `:107-111`); unregistered channels are memory-only. Password rooms: `AccessControlModule.onUserPreJoin` (`src/channel/accesscontrol.js:10-58`), moderators (rank≥2) bypass, plaintext compare (no hashing, `:44`). Identity: guest or account; guest name reuse throttled to **60s** (`config.template.yaml:130`, `src/user.js:363-368`). Rank model: `-1..255`, e.g. `mute:1.5, kick:1.5, ban:2, leaderctl:2, motdedit:3` (`src/channel/permissions.js:4-44`). Abuse controls: per-IP connect rate limit `TokenBucket(5, 0.1)` = burst 5, 1 conn/10s sustained (`src/io/ioserver.js:93-108`); global IP-ban middleware + per-channel ban table (`src/channel/kickban.js:31-70`); Tor exit-node blocking (`src/tor.js`); mod commands `/kick /kickanons /ban /ipban /mute /smute /unmute` (`src/channel/kickban.js:22-27`, `src/channel/chat.js:389-489`).

### watchparty
Room creation: `POST /createRoom` (`server/server.ts:294-330`) generates 3-word name (`words/adjectives|nouns|verbs.txt`, `server/utils/moniker.ts:19-29`). Rooms lazily hydrated from Postgres into in-memory `Map` on first connect, persisted every 1s (`server/server.ts:56-90, 96, 656-697`); idle+empty rooms >8h evicted from memory. Identity: `clientId` (persistent localStorage UUID, no login, `src/utils/utils.ts:293-302`) is primary; optional Firebase `uid` upgrade via `CMD:uid` (`room.ts:244-259`) needed for ownership/lock/subscriber features. Session-spoofing protection: Redis clientId↔sessionId binding, 7-day TTL refreshed on connect (`room.ts:137-185`); strict UUID v4 regex "to prevent prototype pollution" (`:1453-1457`, comment `:161`). Reconnect handling: new connection with existing clientId force-disconnects the old socket (`room.ts:187-190`). Room capacity (`ROOM_CAPACITY`/`ROOM_CAPACITY_SUB`, default unlimited) and per-room password (Postgres-stored, plaintext-cached client-side in localStorage) enforced in namespace middleware (`room.ts:110-130`). `FREE_ROOM_LIMIT:1` vs `SUBSCRIBER_ROOM_LIMIT:20` persistent rooms per user (`server/config.ts:52-53`). **Abuse/rate limiting: ABSENT** — no general rate limiting anywhere (no `express-rate-limit`, no per-socket frequency throttle); only hard per-field length caps (chat ≤10000 chars, username ≤50, host URL ≤50000, etc., `room.ts:826-828, 585, 593, 537`). No IP capture behind reverse proxy (TODO acknowledged, `room.ts:458`).

## 10. What's broken / unmaintained / worth NOT copying

### cytube
- No clock/RTT compensation at all (§3) — leader's own upload latency and followers' download latency both unaccounted for; 2s deadband never notices ~150-300ms systemic lag.
- No playbackRate smoothing — every correction is a jarring hard `seekTo()`.
- Server blindly trusts leader's reported `currentTime` with only an `isNaN` check (`playlist.js:866,869`) — no bounds checking vs. video duration; a buggy/malicious leader can broadcast garbage to the whole room.
- 10+ year old CoffeeScript client player layer raises the bar for new contributions.
- Hand-synchronized dual provider registries (§8), no compile/runtime cross-check.
- Self-documented tech debt: YouTube play/seek/pause "race condition that crashes the player" patched with a manual boolean flag, not a state machine (`player/update.coffee:63-70`); VideoJS player destroyed/rebuilt on every media change because reuse is "pretty glitchy," TODO left unresolved (`player/videojs.coffee:196-199`); `www/js/util.js:945-946` — superstition-driven 100ms polling retry ("I don't trust it"); vestigial `/d` drink-counter module with `// TODO: figure out what to do with this` (`src/channel/drink.js:1`); Vimeo direct-link expiry workaround module shipped but **off by default** (`Config.get("vimeo-workaround")`, unreliable enough not to enable unconditionally, `src/channel/mediarefresher.js:16-60`).
- Chat backlog hardcoded to **15 messages**, not configurable (`src/channel/chat.js:349-351`).
- No autoplay-policy handling — just `console.error` (§15).
- CI targets EOL Node 12/14/15 on a dead provider.

### watchparty
- No general rate limiting / flood control anywhere (chat, room creation, commands) — a genuine gap for an internet-facing self-hosted deploy.
- No automatic hard-seek — drifted viewer must click Sync manually past 10s (§4).
- No conflict resolution for simultaneous commands — true LWW, and unlocked rooms (the default) have zero access control, so any participant, including trolls, can pause/seek/host anyone's stream.
- `YouTube.ts:107` `isSubtitled()` hardcoded `return false` with an acknowledged `// BUG` comment (captions-track state unreliable).
- **Latent privacy bug**: `getRoomState`/`setRoomState` both carry `// TODO only send the password if this is current owner` (`room.ts:1267,1362`) but the code as written sends the plaintext room password to any requester who calls `CMD:getRoomState` — don't repeat this.
- `vBrowserQueue` "queue" comment admits it's not one: `// Not really a queue since there's no ordering, we just retry as long as this is set` (`room.ts:69-70`) — a polling loop masquerading as a queue.
- Heavy bespoke deps (Firebase, Stripe, Discord bot, multi-cloud VM provisioning) coupled directly into `App.tsx`/`room.ts` rather than behind clean optional interfaces.
- `App.tsx` is a single ~2711-line React class component doing sync + chat + WebRTC signaling + mediasoup + VBrowser + playlist + subtitles + settings — a monolith, don't copy the structure even if copying the features.
- TURN credentials hardcoded in client source (`src/utils/utils.ts:165-197`) — a shared dev pool, not a pattern to ship as-is.
- `CHANGELOG.md` stale since April 2023 — don't trust it as a feature inventory.

## 11. Top 5 ideas worth stealing

### cytube
1. **Leader/no-leader hybrid timebase with automatic server fallback** — `src/channel/playlist.js:1079` branch + `:1141-1183` (`_leadLoop`). Cleanly separates "who reports time" from "who may skip/queue"; playback always advances even with zero privileged users connected.
2. **Role-gated echo suppression instead of ignore-flags/sequence numbers** — `player/update.coffee:74-76` + `www/js/util.js:1463-1465`. Trivially correct because only one writer ever emits and it explicitly ignores its own echo.
3. **Deadband + provider-specific accuracy floor** — `player/update.coffee:83-104`, 2s default, 5s Dailymotion floor. Cheap, tunable — worth improving with rate-smoothing and RTT compensation on top, not copying verbatim.
4. **`ChannelModule` plugin lifecycle** — `src/channel/module.js` (`onUserPreJoin/onUserPostJoin/onUserPart/onPreMediaChange/onMediaChange/load/save/packInfo`, `PASSTHROUGH/DENY/ERROR` return codes). Composable-hooks pattern for building room features as independent modules reacting to shared lifecycle events.
5. **Token-bucket rate limiting applied uniformly at multiple layers** — `src/util/token-bucket.js`, reused for per-IP connection throttling (`src/io/ioserver.js:93-108`) and per-user chat flood control (`src/channel/chat.js:27-29`). One reusable primitive at both connection and application layers.

### watchparty
1. **Formal `Player` abstraction with clean method contract** — `src/components/App/Player.ts:1-25` (`getCurrentTime/getDuration/playVideo/pauseVideo/seekVideo/setPlaybackRate/shouldPlay/getTimeRanges/...`). Directly reusable interface shape for a pluggable per-provider adapter design.
2. **Playback-rate drift nudging instead of constant hard-seeking** — `App.tsx:762-781`, 0.5s deadband, `pbr = 1 + delta/10` capped 1.1x, laggards-only. Materially smoother than cytube's hard-seek-only approach; adopt as primary correction with hard-seek as manual fallback.
3. **Median-of-reports "leader" instead of single authoritative clock** — `App.tsx:1954-1959` + `calculateMedian` (`src/utils/utils.ts:342-362`). Robust to one straggler or runaway client; directly matches a "no authoritative user" requirement.
4. **Asymmetric broadcast (excludes sender) + optimistic local apply** — `room.ts:752,763,778` + `App.tsx:1766-1789`. Eliminates the entire echo-suppression problem by construction — no ignore-flags/timeouts/sequence numbers needed.
5. **Cloud shared-browser (VBrowser/Neko) as "any site" fallback** — `server/vm/*`, `src/components/VBrowser/*`. Sidesteps the "find the video element on an arbitrary hostile SPA/iframe/shadow-DOM site" problem entirely by remoting a real browser's audio/video over WebRTC — worth an optional advanced mode for DRM'd/hard-to-adapt sites, alongside a lighter extension-based adapter for the common case.

## 12. Chat subsystem

### cytube
Schema: client→server `TYPE_CHAT = { msg: "string", meta: "object,optional" }` (`src/channel/chat.js:14-17`); broadcast `formatMessage` → `{ username, msg, meta, time: Date.now() }` (`:302-311`). History: `this.buffer`, capped **15 messages** (`:349-351`), replayed on join via `onUserPostJoin` (`:92-94`). Rate limiting (exact constants): default/PM antiflood `MIN_ANTIFLOOD = { burst: 20, sustained: 10 }` (10 msg/s sustained after a 20-burst, `:27-29`); optional per-channel `chat_antiflood_params` default `{ burst: 4, sustained: 1, cooldown: 4 }` (`src/channel/opts.js:20-25`), clamped server-side to max burst 20/sustained 10 (`:54-61`), applied only to rank < 2 (`chat.js:275-280`). Algorithm (`src/utilities.js:135-176` `newRateLimiter().throttle`): free burst, then 1 msg per `1000/sustained` ms, reset if idle > `cooldown`s. New-account chat delays: `new_user_chat_delay` and `new_user_chat_link_delay` (both default 0s) keyed to `user.getFirstSeenTime()` (`chat.js:135-152`). Max message length **320 chars** (`config.template.yaml:132`, truncated `chat.js:165`). Moderation: `/mute`, `/smute` (shadow mute — visible only to self+mods, `:435-465`), `/unmute`, `/kick`, `/kickanons`, `/ban`, `/ipban`, `/clear`, `/rank`, plus link-domain blacklist auto-kick (`:272-279`). Emotes: server-authoritative `EmoteList` per channel (`src/channel/emotes.js:4-92`), each compiled to a regex `(^|\s)<escaped-name>(?!\S)` (`:96-114`), sent as `emoteList` on join; edits gated on `canEditEmotes` (rank 3).

### watchparty
Schema (`global.d.ts:20-46`): `ChatMessage extends ChatMessageBase { id, cmd?, msg?, system?, isSub?, replyToId?, replyToTimestamp?, replyToUserId?, replyToMsg?, timestamp, videoTS?, reactions?: {[emoji]: clientId[]} }`; `id` is sender's clientId, `cmd` doubles chat as an activity/system-event log (`"play"/"pause"/"seek"/"host"/"lock"/...`). ## 14. Production lessons

### cytube
- **Reconnect storms**: per-IP connection token bucket `TokenBucket(5, 0.1)` (`src/io/ioserver.js:93-108`); `pingTimeout` deliberately raised to 120000ms specifically to avoid "spurious reconnects during transient network issues" (cites GH #780, `:266-273`). No custom client-side backoff — relies on socket.io defaults (`www/js/callbacks.js:1264`). **No incremental resync**: reconnect = full `joinChannel` re-emit, server resends full playlist + `changeMedia` + chat backlog + emote list from scratch via each module's `onUserPostJoin` — full-state re-transfer every time, not a delta.
- **Clock drift over long sessions**: not specifically handled — the 5s-interval deadband-seek is inherently self-correcting regardless of session length, papering over drift accumulation via periodic hard seeks rather than preventing it (§3/§4).
- **Backgrounded/throttled tabs**: **ABSENT** — no `visibilitychange`/`requestAnimationFrame` compensation anywhere; leader's `sendVideoUpdate` interval (`www/js/callbacks.js:601`, 5000ms) and server's `_leadLoop` (`playlist.js:1131-1134`, 1000ms) are ordinary timers with no defense against background-tab throttling — a backgrounded leader silently stops reporting accurately.
- **Autoplay policy**: effectively unhandled, see §15.

### watchparty
- **Reconnect storms**: force-disconnect the previous socket for a reconnecting `clientId` (`server/room.ts:187-190`) + Redis session-id binding with refreshed 7-day TTL (`:137-185`). Client relies on socket.io's built-in auto-reconnect with no custom backoff/jitter on top; UI shows a "Reconnecting..." banner (`App.tsx:375-384`).
- **Clock drift over long sessions**: mitigated only by the continuous 1Hz playbackRate-nudge loop (§4) — no periodic re-anchoring against a server clock, no NTP-style correction, no automatic hard-reseek; drift beyond 10s requires the user to click Sync.
- **Backgrounded/throttled tabs**: **ABSENT/unhandled** — the only `visibilityState` check in the whole codebase gates whether to play a chat-notification sound (`App.tsx:698-706`), unrelated to sync. The 1Hz heartbeat (`App.tsx:866-871`) is an ordinary `setInterval` with no Page Visibility compensation, no Web Worker, no catch-up logic when a tab returns from background.
- **Autoplay policy**: handled proactively — see §15.

## 15. Autoplay policy handling

### cytube
**Largely ABSENT.** Providers whose native `play()` returns a Promise (Vimeo, PeerTube embeds) attach a bare `.catch()` that only logs to console, no retry/fallback/UI:
```coffee
# player/vimeo.coffee:44-47
play: ->
    @paused = false
    @vimeo.play().catch((error) -> console.error('vimeo::play():', error)) if @vimeo
```
Same pattern `player/peertube.coffee:78-82`. YouTube, VideoJS/raw-file, Twitch, SoundCloud, PlayerJS, Niconico, Dailymotion call `.play()` synchronously with **no promise/error handling at all**. No muted-autoplay fallback exists anywhere (no code sets `muted=true` in response to a play failure — all `.muted` reads found are volume-getters, not autoplay-recovery writes). No click-to-unmute/click-to-play prompt UI. Practical effect: a remote "play" arriving without a prior gesture on that tab simply fails to start in browsers with strict autoplay policies, silent except for a console error; the user must click the embedded player's own native controls, after which the next `mediaUpdate` tick hard-seeks them back into sync.

### watchparty
**Handled proactively.** Uses the `can-autoplay` npm package to probe capability once on mount (`const canAutoplay = await testAutoplay()`, `App.tsx:289-290`, `testAutoplay` = `(await canAutoplay.video()).result`, `src/utils/utils.ts:128-131`), then before every local play re-checks and **auto-mutes to force autoplay success**:
```js
// App.tsx:1705-1731
localPlay = async () => {
  const canAutoplay = this.state.isAutoPlayable || (await testAutoplay());
  this.setState({ roomPaused: false, isAutoPlayable: canAutoplay }, async () => {
    if (!this.state.isAutoPlayable || (this.localStreamToPublish && !this.isLocalStreamAFile)) {
      this.localSetMute(true);
    } else { this.localSetMute(false); }
    try { await this.Player().playVideo(); }
    catch (e: any) {
      if (e.name === "NotSupportedError" && this.usingNative()) {
        this.setState({ loading: false, nonPlayableMedia: true });
      }
    }
  });
};
```
`.play()` rejection is caught; only `NotSupportedError` gets dedicated UI (`nonPlayableMedia` state) — a plain autoplay-blocked `NotAllowedError` is caught and `console.warn`'d but otherwise silently swallowed, with no explicit "click to play" overlay (the existing play/pause button implicitly serves as recovery, since `roomPaused` isn't forced back to `true` on failure). Relies on the "muted autoplay is always allowed" browser exemption as its primary strategy; no extension-privilege bypass exists (there is no extension).
